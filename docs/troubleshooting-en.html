Upgrade stops at git fetch failed (would clobber existing tag)

Symptom　jtdt update prints git fetch failed and stops; the service is rolled back to the previous version, with no hint as to why.

Cause　This project's git history was rewritten on 2026-09-13 (to remove a piece of data that should never have been committed), so every tag now points at a new commit. While the local tags still point at the old ones, git fetch --tags (without --force) reports would clobber existing tag for each and exits with code 1.

What to do　Run this once and it is fixed for good (it only touches refs inside .git — your data is never touched):

Linux / macOS
sudo git -C /opt/jt-doc-tools fetch --tags --force origin
Windows (run PowerShell as Administrator)
git -C "C:\Program Files\jt-doc-tools" fetch --tags --force origin

Unaffected: tarball installs (no .git), the Windows installer, and anything installed after 2026-09-13. Fixed from v1.15.41.

Health check timed out / failed (but the service is actually fine)

Symptom　The last step of the upgrade times out, yet the site opens in a browser.

Cause　After changing the listen address or port (jtdt bind), older versions read the address from the environment of the shell running the upgrade — where it was never set — so they always probed 127.0.0.1:8765. A corporate http_proxy can also send "connect to myself" through the proxy.

What to do　Fixed in v1.15.15 (it reads the service manager's own configuration, connects directly, and prints which addresses it probed plus the last 20 log lines). Upgrade to at least that version; if it still times out, read the end of jtdt logs.

Another case　Updating from v1.15.11 through v1.16.10 ends with Health check failed while Service state says RUNNING / active; on Windows it also says no log was found.

Cause　The health check in those versions was itself broken (a missing import), so it reported failure whether or not the service was up. Windows and macOS also looked for the log in the wrong place.

What to do　If the page opens in a browser, the update succeeded and nothing needs fixing. Fixed in v1.16.11, but the update to v1.16.11 itself still prints this message once (the check is run by the version you are updating from); from the next update on it is gone. Where the logs actually are: Windows C:\ProgramData\jt-doc-tools\Logs\ (jtdt-svc.err.log and jtdt-svc.out.log), macOS ~/Library/Logs/ (jt-doc-tools.err and jt-doc-tools.log), Linux journalctl -u jt-doc-tools.

CERTIFICATE_VERIFY_FAILED (corporate TLS inspection)

Symptom　Certificate verification fails during an upgrade, while downloading OCR language files, or when connecting to an LLM / SSO.

Cause　A corporate TLS-inspection proxy replaces external certificates with its own CA, which Python and uv do not trust by default.

What to do　The program hooks into the operating system's trust store automatically (truststore), so most environments need no configuration. If it still fails, import the corporate CA into the OS trust store; JTDT_TLS_INSECURE=1 bypasses verification temporarily (only on a network you trust).

An install without git cannot update

Symptom　jtdt update says git is missing, or that this is not a git repository.

Cause　Without git on the machine, the one-line installer falls back to downloading an archive, so the installation has no .git.

What to do　Install git and run the one-line installer again — it adopts the existing directory into a git repository (your .venv and data are kept), after which updates work normally.

Windows cannot find git, or asks you to install it with winget

Symptom　git was just installed but still cannot be found; or Windows Server has no winget.

Cause　A freshly installed program only updates PATH in the registry — terminals that are already open (including new tabs) still see the old one; and Windows Server 2019 / 2022 ship without winget.

What to do　Simply run it again — no reboot needed: the program looks in PATH, then the registry, then the standard install locations. On Server editions, download the installer from the git website.

[X] uv venv failed (when upgrading on Windows)

Symptom　Installing over an existing installation fails; a silent install appears to hang.

Cause　The service is still running and python.exe holds the virtual environment's files open, so they cannot be deleted. Older failure dialogs had no silent-mode default, so they waited for a button nobody could press.

What to do　Fixed in v1.15.37 (the service is stopped and its handles released before anything is deleted, and every dialog has a silent default). If it hangs, stop the service manually first; the installer's own log is at C:\ProgramData\jt-doc-tools\Logs\installer.log.

Not enough disk space during an upgrade

Symptom　The backup step fails — and the service has already been stopped.

Cause　Upgrades take a full backup of the data directory and keep three of them.

What to do　From v1.15.17 the space is checked before the service stops, and the message says how much is missing; the backup also skips anything that rebuilds itself (the company-ID database, temporary files, job results) — measured 1.93 → 0.56 GB per backup. Free up space and run it again.

attempt to write a readonly database

Symptom　After running a CLI command with sudo, the service can no longer write to the database.

Cause　Files created while running as root belong to root, while the service runs under its own account. The easiest one to hit is jtdt reset-password — the rescue command locks you out.

What to do　From v1.15.16 every CLI command restores ownership of the data directory when it finishes. On older versions, fix the ownership by hand (Linux: sudo chown -R jtdt:jtdt <data directory>).

Conversions return 503, or Chinese text comes out as empty boxes

Symptom　Office-related tools return "service temporarily unavailable"; or Chinese characters in the produced PDF are hollow boxes.

Cause　This machine is missing LibreOffice / OxOffice, or CJK fonts.

What to do　The error message names what to install. On Linux install libreoffice (or OxOffice) and fonts-noto-cjk; the admin area's "system dependencies" page lists exactly what is missing.

Remote users get "CSRF token missing or incorrect" as soon as they upload

Symptom　Everything works when tested on the server itself; only connections from another machine fail. Sign-in may also bounce back to the login page.

Cause　The reverse proxy sets X-Forwarded-Proto to a fixed https while the site is actually http — so the backend marks cookies Secure and the browser drops them over plain http. http://localhost is a secure-origin exception, which is why it cannot be reproduced on the server itself.

What to do　Make the reverse proxy pass the real protocol (on IIS, use a rewriteMap to translate {HTTPS} into https/http), or serve the site over HTTPS. Examples are in OPS.md.

“Cannot reach the speech service” or a connection timeout

Symptom　“Test the connection” fails on the speech service settings page; the recognition profile dropdown shows “Could not read the list: Cannot reach the speech service”; or submitting a recording fails.

Cause　The endpoint is wrong (host, port, http or https), a firewall is in the way, or their service is down. It can also be certificate verification: when they use a self-signed certificate, the connection is refused at the TLS step, and the screen still only says it cannot reach them.

What to do　Paste the endpoint exactly as they gave it (for example https://host:8790/api/v1). On the machine running this system, try curl https://host:8790/api/v1/health: if it cannot connect, the problem is the network or the address; if it only connects with -k, the problem is the certificate. Paste their certificate (PEM) into “Their certificate”, and save only after checking it against the SHA-256 fingerprint they publish. Do not work around it by turning verification off: every submission hands over the API key, and with verification off anyone can impersonate them.

“The speech service rejected this API key (401)” or “it lacks permission for this action (403)”

Symptom　One of these appears when testing the connection or submitting.

Cause　These are two different situations. 401: the key is mistyped, was revoked on their side, or was pasted as a whole header. 403: the key is correct, but it does not have permission for this action; checking for typos or revocation will not find anything. Their health check cannot reveal either, because it does not check the key; that is why “Test the connection” also asks once with the key.

What to do　401: put only the key itself in “API key” (the string they gave you; this system builds the Authorization: Bearer header itself, and a pasted prefix is removed automatically), and if it is still rejected, ask them to confirm the key is still valid. 403: ask their administrator to grant the key the permission; which one is missing is written to this system's service log (jtdt logs).

“The speech service does not accept this machine's address. Ask your administrator to add the public address for recordings to its allow list.”

Symptom　Submitting a recording fails, and the message ends with a host name.

Cause　The speech service only fetches recordings from addresses on its allow list, and this system's audio base address is not on it.

What to do　Give the host name at the end of the message to the speech service administrator to add to the allow list. If you change the audio base address, ask them to add the new one too: the same system may be reachable both directly on the internal network and through a reverse proxy, and whichever one you fill in is the one they see.

“Could not reach our recording URL” or “the link had already expired”

Symptom　Submitting a recording fails with “The speech service could not reach our recording URL”, “The link had already expired when the speech service came to fetch the recording”, or “We rejected the speech service when it came to fetch the recording (401 / 403)”.

Cause　The recording is not pushed to them; they come back and fetch it. This system hands them a short-lived signed URL (/api/speech/audio/…?exp=…&sig=…, no sign-in, expires by itself). If the audio base address is a name only the browser machine can reach (such as localhost), a firewall or reverse proxy is in the way, or the reverse proxy puts a sign-in in front, they cannot fetch it.

What to do　Fill in an audio base address that is reachable from the speech service machine (the settings page never derives it from the browser address; guessing wrong would make it work for some people and not others). If the reverse proxy puts SSO, Kerberos or another sign-in in front, let /api/speech/audio/ through; it is already protected by the signature. An expired link is not caused by queueing: they fetch the file as soon as the job arrives and never fetch that URL again, however long it waits. It usually means retrying or waiting too long before submitting; submit again.

Stuck at “Queued (N ahead)”, or “Waited N minutes and the speech service has not reported a result, so the job was cancelled on their side”

Symptom　After submitting, the transcription keeps showing Queued; or once its turn comes it runs for a long time and finally fails with the message above. You may also see “The speech service queue is full; submit again later”.

Cause　The speech service GPU handles one job at a time and queues the rest, and the jobs ahead include other people's. While queued, the page shows how many are ahead, and that time does not count towards the waiting limit; once its turn comes, recognition and correction progress moves. This system only starts timing after the job's turn comes (the larger of 15 minutes and half the recording length) and asks them to cancel the job once that is exceeded; the queue itself is waited on for at most 4 hours.

What to do　While queued, wait for its turn; for very long recordings, avoid times when someone else is sending a long meeting. If it times out after its turn came, or queues for more than 4 hours, ask the speech service side to check the GPU server.

“The speech service reported success but returned no transcript segments”

Symptom　Transcription fails with this message, even though people clearly speak in the recording.

Cause　The speech service restarted (an update or a crash) while sending the recognition result back, and a partial result was taken as complete, most often with no segments at all. This system always treats zero segments as a failure; it never hands over an empty transcript as a success.

What to do　Submitting again usually works. If it keeps happening, ask the speech service side whether the server is being updated or restarted.

A long stretch with no text at the end　When the last minute or more of a recording has no text at all, the result page says how long that gap is. Since 2026-09-23 the speech service no longer returns only the first part of a transcript, so this hint now mostly means the recording was left running, or it ends with applause or music. If people really were speaking during that time, submit again.

“The speech service does not accept this language setting”

Symptom　After choosing a language, the job fails as soon as it is submitted.

Cause　The speech service only accepts the languages its current recognition mode supports. Before v1.16.8 the page sent Chinese as zh, while the service expects zh-Hant, so every job with Chinese selected was rejected (fixed in v1.16.9). If it still happens, the recognition mode chosen by the administrator most likely does not support that language (for example, the Taiwanese mode only accepts Taiwanese and Chinese).

What to do　Choose Detect automatically and submit again. If it keeps happening, ask your administrator to check which languages the current recognition mode supports under Speech service (JTLW) (they are listed once a recognition mode is selected).

A Chinese meeting recognised as English throughout (or the other way round)

Symptom　Most of the transcript is wrong characters, or the whole meeting came out in another language; the language was set to Detect automatically.

Cause　Detect automatically only listens to about the first 30 seconds of speech to decide which language to use for the whole recording. If someone speaks another language at the start (for example an English opening; 20 seconds is enough), the whole meeting is recognised in the wrong language. The speech service measured a meeting that was mostly Chinese but opened in English: the error rate on Chinese sentences went from 15% to 88%. Silence or background noise at the start does not matter, so there is no need to trim it.

What to do　Set Language to the language used throughout the meeting and submit again. For meetings that alternate between Chinese and English sentences, pick the language used most: whole sentences in the other language are mostly not recognised correctly (English terms inside Chinese sentences are fine).

Meeting recording to transcript is greyed out, or says “The speech service is not set up yet”

Symptom　The tool cannot be opened from the sidebar or the home page; opening its page only shows a setup notice.

Cause　The tool depends on an external speech service. While it is not enabled in the admin area, or the endpoint and API key are incomplete, it stays greyed out on purpose, so there is never an upload box that looks normal and only fails after you press it.

What to do　In the admin area, open Speech service (JTLW), tick enable, fill in the endpoint, API key and audio base address, press “Test the connection”, then save. The other 49 tools are not affected.
