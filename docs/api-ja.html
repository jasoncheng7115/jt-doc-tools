API 利用ガイド

Jason Tools ドキュメントツールボックスは外部に RESTful API を提供しており、すべてのツールに対応するエンドポイントがあります。自動化のフロー、自社システム、スケジュール処理に組み込めます。

基本方針：API は既定では認証なしで使えます（web UI と同じ公開範囲です）。制限が必要なときは、管理者が admin の「API Token」ページで enforce モードを有効にし、bearer token を発行します。

1. 認証

認証を有効にしない（既定）

新規インストールでは既定で認証が無効なため、すべての /api/* をそのまま利用でき、token は不要です。

1. 認証

API token を有効にする

管理者は admin → API Token へ移動します：

  1. 「新しい token を発行」をクリック → 用途の名称を入力（例 gitlab-ci）→ 64 文字の hex token を受け取ります（一度しか表示されないので保存してください）
  2. 「Enforce —— token を持たないものはすべて拒否」にチェックを入れて保存します

以降、すべての /api/* には次のいずれかの形式が必要です：

Authorization: Bearer 64char-hex-token-here

または query string：

GET /api/jobs/abc123?token=64char-hex-token-here

token がない、または無効な場合 → 401 Unauthorized の JSON：

{"ok": false, "detail": "需要有效的 API token（Authorization: Bearer ...）"}

Token は admin / jtdt CLI で管理し、web 認証 (jtdt-admin / LDAP / AD) とは完全に独立しています。

3. 文書変換 API

オフィス文書 → PDF

オフィス文書を PDF に変換します（OxOffice / LibreOffice エンジンを使います）。

POST /api/convert-to-pdf
パラメータ種類必須説明
filefile✓オフィス文書 の文書
curl -X POST http://localhost:8765/api/convert-to-pdf \
  -H "Authorization: Bearer YOUR_TOKEN" \
  -F "file=@報告.docx" \
  --output 報告.pdf

レスポンス：PDF のバイナリ（application/pdf）。失敗時は 4xx + JSON {"detail": "..."}。

3. 文書変換 API

オフィス文書の形式変換

同じ種類の文書どうしの形式変換：文書ファイル↔文書ファイル、表計算↔表計算、プレゼンテーション↔プレゼンテーション。job モードで job_id を返します。

先に利用できる変換先の形式を問い合わせてから変換を送信してください。 target の値はインストール環境によって異なるため（Impress モジュールがなければプレゼンテーションの組は現れません）、id を自分のプログラムに固定で書かないでください：

GET /tools/office-convert/formats
curl -s http://localhost:8765/tools/office-convert/formats \
  -H "Authorization: Bearer YOUR_TOKEN" | jq
# → {"families": [{"id": "text", "name": "文書檔",
#                  "sources": ["odt", "docx", ...],
#                  "targets": [{"id": "docx-2007", "ext": "docx",
#                               "label": "Word 2007", "note": "...",
#                               "common": true}, ...]}, ...]}
POST /tools/office-convert/convert
パラメータ種類必須説明
filefile✓オフィス文書。複数回指定できます（複数の場合は ZIP にまとめます）
targetstr✓変換先の形式 id。上の formats から取得します

同じリクエストの中のファイルは同じ種類でなければなりません（表計算と文書ファイルを混ぜて送ることはできません）。また target の属する種類とも一致している必要があり、そうでない場合は 400 を返します。

# 文書檔：.odt 轉成 Word 97–2003
curl -X POST http://localhost:8765/tools/office-convert/convert \
  -H "Authorization: Bearer YOUR_TOKEN" \
  -F "file=@報告.odt" -F "target=doc" | jq
# → {"job_id": "...", "download_url": "/api/jobs/.../download"}

# 簡報：.pptx 轉成 ODF 簡報
curl -X POST http://localhost:8765/tools/office-convert/convert \
  -H "Authorization: Bearer YOUR_TOKEN" \
  -F "file=@簡報.pptx" -F "target=odp" | jq

.docx / .xlsx / .pptx にはそれぞれ 2 つの変換先があり、違いは次のとおりです互換モード名称だけの違いではありません：

変換先の id出力互換モード
docx-2007Word 2007 の書き方12
docx-365Word 2010–365 の書き方15
xlsx-2007 / xlsx-ooxmlExcel 2007–365 / Office Open XML—
pptx-2007 / pptx-ooxmlPowerPoint 2007–365 / Office Open XML—

レスポンス：{"job_id": "...", "download_url": "..."}。1 ファイルなら元の形式、複数なら ZIP を返します。 失敗時は 4xx + JSON {"detail": "..."}。

3. 文書変換 API

PDF → 画像

PDF やオフィス文書の各ページを PNG / WebP / JPEG に変換します（複数ページは ZIP にまとめます）。サイズは DPI で指定するか、幅を直接指定できます（すべてのページを同じ幅に拡大縮小し、高さはページの縦横比に合わせます）。

POST /tools/pdf-to-image/convert
GET  /tools/pdf-to-image/download/{upload_id}
パラメータ種類必須説明
filefile✓PDF またはオフィス文書（PDF 以外はまず PDF に変換）
formatstring出力形式：png（既定）/ webp / jpeg（jpg も可）。それ以外の値は 400
widthint各ページの幅（ピクセル、16～10000）。指定すると dpi は無視します。範囲外は 400 を返し、黙って別の幅にはしません
dpiintwidth を指定しないときの解像度。既定 200、範囲 72～600
qualityintWebP / JPEG の画質 1～100、既定 80。PNG は可逆圧縮なので使いません

1 ページが 4000 万ピクセルを超える場合（WebP では一辺が 16383 ピクセルを超える場合。形式そのものの上限です）は縮小して出力し、そのページの reduced が true になります。どのページかはトップレベルの reduced_pages に列挙されます。

# 1. 上傳並轉換（網頁用：WebP、寬 1920）
curl -X POST http://localhost:8765/tools/pdf-to-image/convert \
  -H "Authorization: Bearer YOUR_TOKEN" \
  -F "file=@slides.pdf" -F "format=webp" -F "width=1920" | jq
# → {"upload_id": "...", "page_count": 3, "format": "webp", "size_mode": "width",
#    "width": 1920, "dpi": null, "reduced_pages": [], "pages": [{"width_px": 1920, ...}]}

# 依 DPI 轉 PNG
curl -X POST http://localhost:8765/tools/pdf-to-image/convert \
  -H "Authorization: Bearer YOUR_TOKEN" \
  -F "file=@document.pdf" -F "dpi=200" | jq

# 2. 下載
curl -s http://localhost:8765/tools/pdf-to-image/download/abc123 \
  -H "Authorization: Bearer YOUR_TOKEN" --output pages.zip

レスポンス：手順 1 は各ページの情報（width_px / height_px / dpi / size_bytes / reduced）と upload_id を返します。手順 2 で画像を取得します。1 ページなら選んだ形式の画像、複数ページなら ZIP です（各ページのファイル名は slides_p1.webp のようになります）。

PDF を Word（.docx）または OpenDocument（.odt）に逆変換します。job モードで job_id を返します。

POST /tools/pdf-to-office/convert
パラメータ種類必須説明
filefile✓PDF
output_formatstrdocx（既定）/ odt
enginestr変換エンジン：pdf2docx-refine（既定、安定）/ jtdt-reform（自社のレイアウト再構成）/ jtdt-layout（レイアウト再現：LibreOffice/OxOffice Draw で正確にインポートし、自社の変換エンジンで docx/odt に再構成します。レイアウトがほぼ 1:1 のページ固定テキストボックスで、画像 / 枠線を含みます。本質はフロー型のテキストではなく、本物の表もありません）
enable_postprocessboolpdf2docx-refine のみ有効：jtdt-refine の後処理（25 の fixer）を適用するか。既定は false
# 預設引擎 pdf2docx-refine
curl -X POST http://localhost:8765/tools/pdf-to-office/convert \
  -H "Authorization: Bearer YOUR_TOKEN" \
  -F "file=@form.pdf" -F "output_format=docx" \
  | jq
# → {"job_id": "...", "download_url": "/api/jobs/.../download"}

# 改用自家 jtdt-reform 引擎
curl -X POST http://localhost:8765/tools/pdf-to-office/convert \
  -H "Authorization: Bearer YOUR_TOKEN" \
  -F "file=@form.pdf" -F "output_format=odt" -F "engine=jtdt-reform" \
  | jq

# 改用 jtdt-layout 版面重現引擎（表單 / 多欄 / 含框線表格版面最接近原 PDF）
curl -X POST http://localhost:8765/tools/pdf-to-office/convert \
  -H "Authorization: Bearer YOUR_TOKEN" \
  -F "file=@form.pdf" -F "output_format=odt" -F "engine=jtdt-layout" \
  | jq

レスポンス：{"job_id": "...", "download_url": "..."}。その後は第 10 章の job API でポーリングして結果を取得します。

変換の前後を比較するサムネイルの取得：job の完了後、GET /api/jobs/{job_id} の meta.preview に page_indices（プレビュー対象の 0 始まりのページ番号の一覧。6 ページ以下なら全部、7 ページ以上なら先頭 2 + 中央 2 + 末尾 2）、 orig_pages、result_pages、orig_chars、result_chars が含まれます。ページごとのサムネイルは次で取得します：

GET /tools/pdf-to-office/preview/{job_id}/orig/{page}     # 轉換前（原 PDF）
GET /tools/pdf-to-office/preview/{job_id}/result/{page}   # 轉換後（docx/odt 渲染）

page は 1 始まりのページ番号です（次に対応します page_indices の要素 +1）。次を返します image/png。

# 完成後讀 preview 頁碼清單
curl -s http://localhost:8765/api/jobs/$JOB \
  -H "Authorization: Bearer YOUR_TOKEN" | jq '.meta.preview'
# 取第 1 頁的前 / 後對照縮圖
curl -s http://localhost:8765/tools/pdf-to-office/preview/$JOB/orig/1 \
  -H "Authorization: Bearer YOUR_TOKEN" --output before_p1.png
curl -s http://localhost:8765/tools/pdf-to-office/preview/$JOB/result/1 \
  -H "Authorization: Bearer YOUR_TOKEN" --output after_p1.png

4. PDF 編集 API

PDF → プレゼンテーション

PDF を PowerPoint（.pptx）または OpenDocument プレゼンテーション（.odp）に逆変換します。1 ページが 1 枚のスライドに対応し、 スライドサイズは原本のままです（縦向きの PDF もそのまま再現します）。job モードで job_id を返します。

エンジンは 1 つだけ（jtdt-layout のレイアウト再現）のため、engine パラメータはありません。

POST /tools/pdf-to-slides/convert
パラメータ種類必須説明
filefile✓PDF
output_formatstrpptx（既定）/ odp
curl -X POST http://localhost:8765/tools/pdf-to-slides/convert \
  -H "Authorization: Bearer YOUR_TOKEN" \
  -F "file=@deck.pdf" -F "output_format=pptx" \
  | jq
# → {"job_id": "...", "download_url": "/api/jobs/.../download"}

# 輸出 OpenDocument 簡報（物件多時比 .pptx 快）
curl -X POST http://localhost:8765/tools/pdf-to-slides/convert \
  -H "Authorization: Bearer YOUR_TOKEN" \
  -F "file=@deck.pdf" -F "output_format=odp" \
  | jq

前後比較のサムネイルは pdf-to-office と同じです：

GET /tools/pdf-to-slides/preview/{job_id}/orig/{page}     # 轉換前（原 PDF）
GET /tools/pdf-to-slides/preview/{job_id}/result/{page}   # 轉換後（簡報渲染）

環境の要件：office スイートの次が必要です Impress モジュール（oxoffice-impress / libreoffice-impress）。モジュールがないと「変換は成功したのに出力が見つからない」という状態になります。 「設定 → 依存パッケージの確認」で確認できます。

固有名詞（v1.16.39 から）は音声サービスに用語集として送り、校正で使います。正しい表記はそのまま残し、つづりの近い聞き間違いは書いた表記に直します（音声サービスのインターフェース版 2.8 から、句読点のみの校正でも直します）。1 行に 1 語が最適です（Proxmox、PVE、Proxmox VE をそれぞれ 1 行）。つづりが大きく違う聞き間違いは校正で直せないことがあります。認識ではこのリストを参考にしません。音声サービスの実測で、リストの語がその会議に出てこないと、認識がその語を文字起こしに勝手に挿入することがわかったため採用していません。重複（大文字小文字を区別しない）は最初の 1 つだけ、順序は指定どおりです。最大 500 個で、超えると 400 を返し、黙って切り捨てることはありません（切り捨てた語は使われないのに、呼び出し側は送ったと思ってしまうため）。

既知の聞き間違い（v1.16.49 から）：聞き間違え方が分かっている語は「聞き間違えた表記 → 正しい表記」の形で 1 行に書きます（矢印は -> や => でも可。聞き間違えた表記が複数あるときは読点かカンマで区切ります）。例：Proksmox、Proxmux → Proxmox。音声サービスが校正の前に表のとおり置き換えます。言語モデルを通さず、どの校正レベルでも行い、元の認識層は変わりません。つづりが大きく違って校正では認識できない聞き間違いは、この方法でしか直せません。英語は語全体が一致したときだけ、大文字小文字を区別せずに置き換え、中国語は文字どおりに置き換えます。中国語の聞き間違えた表記が短すぎると別の語の一部まで置き換わることがあるため、具体的に書いてください。正しい表記も固有名詞として送ります。規則は音声サービスに合わせています。1 語につき聞き間違えた表記は最大 20 個、それぞれ 2～200 文字。矢印の右側は 1 語だけ（読点・カンマ・セミコロン・|・／、片側に空白のある / で区切ると複数の語になります。TCP/IP は 1 語です）。聞き間違えた表記がリスト上の別の固有名詞であってはいけません（置き換えると正しく書かれた語まで変わるため。リストに Proxmox VE / PVE と書いた行は Proxmox VE と PVE の 2 語として数えます）。同じ聞き間違えた表記を 2 つの語に対応させることもできません。これに反する行は 400 を返してどの行かを示し、送信しません。矢印が 2 つ以上ある行、# で始まる行、文になっている行は、これまでどおり会議の背景として扱います。音声サービスのインターフェース版 2.9 から受け付けます。それより古い版（または版を取得できないとき）は送信せず、応答の variants_sent が false になります。

文として書いた行は固有名詞として送りません（v1.16.44 から）。句点・感嘆符・疑問符がある行や、区切った一部が 40 文字 / 漢字 10 文字を超える行は、会議の背景として扱います。文全体を固有名詞にしても、校正でそのまま残したり、つづりの比較に使ったりする意味がないためです。「與會者：王小明、Bianca」のような行は、コロンの前のラベルは送らず、後ろを語の並びとして送ります。ラベルだけの行（「與會人員如下：」）は送りません。# で始まる見出し行と、文字を含まない日付・時刻・数字だけの部分も送りません（v1.16.48）。全文は応答の context に入り、会議の要約へ送るときに会議の背景に入ります。

発言者分離の方式は音声サービスのバージョンで決まります（v1.16.31 から）：音声サービスのインターフェース版が 2.5 以上なら、本システムは NVIDIA Nemotron での識別を依頼します。2.4 以前（または版を取得できない）場合は従来の方式です。レスポンスの speaker_engine に、このジョブで依頼した方式が入ります。音声サービスが同じ実際の認識結果で測定した値（人数指定なし）：中国語の会議 20 件で話者の誤りが 18.52% → 2.92%、英語の会議 16 件で 12.31% → 4.65%。

同じ num_speakers でも、2 つの方式では意味が逆になります：

Nemotron（speaker_engine = auto）従来の方式（legacy）
入力した数上限としてのみ使われる：検出した人数がそれより多いときだけ統合し、少ないときはそのまま必ずその数のグループに分ける
実際より多い影響なし主な発言者が分割される
実際より少ない別の人が同じ話者にまとめられる別の人が同じ話者にまとめられる
おすすめ不明なら 0 のまま。少なめより多めに不明なら 0 のまま。一言二言しか話さない人は数えない

Nemotron では、正しい人数を指定しても指定しない場合との差は 0.01 ポイントだけです（20 件、95% 信頼区間 [−0.03, 0.00]）。「劣らない」としか言えないので、精度を上げるために入力する必要はありません。

新しい方法で識別できる発言者は最大 8 人です。8 人を超える人数を指定すると、音声サービスは必ず従来の方法に切り替えます。指定しない場合は、新しい方法の 8 人分の枠がすべて埋まり、かつ従来の方法で 8 人を超えて識別されたときだけ切り替え、それ以外は新しい方法のまま最大 8 人で識別します。切り替えた場合、理由はレスポンスの diarization.reason（コード）と diarization.note（説明）に入ります。8 人を超えることが確実な会議では人数を指定してください。

auto は録音の冒頭約 30 秒の発話だけを聞いて、会議全体の言語を決めます。区間ごとに判定するわけではありません。冒頭で誰かが別の言語を話すと（20 秒で十分です）、会議全体が誤って認識されることがあります。冒頭の無音や雑音は影響しません。会議全体の言語が分かっている場合は指定してください。中国語と英語の文全体が入れ替わる会議では、多く使われている方の言語を指定してください。もう一方の言語の文はほとんど正しく認識されません（中国語の文の中に英語の用語が混ざる程度なら問題ありません）。

このエンドポイントは同期処理です。37 分の会議で実測 7〜8 分（認識 ＋ 発言者分離 ＋ 校正）かかるため、呼び出し側のタイムアウトは長めにしてください。バックグラウンド処理が必要な場合は Web 側の経路（POST /upload → POST /start → ジョブ ID で /api/jobs/{id} をポーリング）を使ってください。

要約の grounded は、要約中の数字と英単語がすべて文字起こしの中に見つかることを表します。見つからないものは unsupported に並びます（言い回しが忠実かどうかは、段番号を手がかりに人が確認するしかありません）。

パラメータ種類必須説明

  -F "file=@meeting.vtt" \

{
  "terms": ["王小明", "Bianca"],
  "suggestions": [
    {"from": "Bianka", "to": "Bianca", "count": 2, "seqs": [2],
     "example": "報價我已經寄給 Bianka 了，Bianka 會再確認。"},
    {"from": "王曉明", "to": "王小明", "count": 1, "seqs": [1],
     "example": "王曉明今天要報告第四季的預算。"}
  ]
}

照合のルールは固定で、提案しすぎないほうに倒してあります。英語は 1～2 文字違い、または途中に空白やハイフンが入ったもの。中国語は 3～8 文字で、すべての文字の読みが一致するもの（同音異字）。大文字・小文字だけの違い、単数・複数、2 文字の語、背景自体がその表記を使っているもの、2 つの語のどちらとも取れるものは提案しません。

選んだものを /api/meeting-summary の replacements に入れると分析の前に適用されます。英語は単語単位で置き換え（Biankas の一部が置き換わることはありません）、レスポンスに replacements（実際に置き換えた内容と件数。1 件も一致しなかったものは含みません）が加わります。Web 画面からエクスポートした .json には文字起こしが含まれ、置き換えた段落は元の文を orig_text に残します。

提案で見つからない表記（認識の聞き間違いが大きい場合。例：Proxmox が Groxmoxity になっている）も、自分で replacements に入れられます。規則は同じです。英語の置き換えは大文字小文字を区別するため、小文字の groxmoxity も置き換えるには別に 1 組追加してください。

curl -X POST http://localhost:8765/tools/meeting-summary/api/meeting-summary \
  -H "Authorization: Bearer YOUR_TOKEN" \
  -F "file=@meeting.vtt" \
  -F "context=與會者：王小明（財務長）、Bianca（PM）" \
  --form-string 'replacements=[{"from": "Bianka", "to": "Bianca"}]' | jq '.replacements'
# → [{"from": "Bianka", "to": "Bianca", "count": 2}]

  • ヘッダーには既定で「草稿」と入り、draft_mark を false にすると入りません。ファイル名には title を使い（最大 40 字。ファイル名に使えない文字は取り除きます）、ダウンロードされるファイル名は <title>-草稿.<fmt> です。
  • フォントは標楷體です。サーバーに標楷體がない場合、PDF はほかの楷書体、それもなければ明朝体を使います。
  • JSON には "format": "jtdt-official-doc" と "format_version": 1 が付き、案件全体が入ります。draft.text は送った文章に置き換え、draft.issues はその文章で照合し直したものです。
  • 電子公文書の DI ファイル（di）は台湾の政府電子公文書の本文ファイル（XML）で、国家発展委員会檔案管理局「文書及び檔案管理電算化作業規範」104 年版 DTD（公文 104_2_utf8.dtd、伺い文 104_5_utf8.dtd）に従います。担当者が機関の公文書システムに取り込み、通常どおり番号取得・決裁・発信を行います。発信日・文書番号は空欄なら空欄のまま、記入があればそのまま入れます。機関コードはまず org_codes、なければ名称でアドレス帳を引きます（正式名称が完全一致する機関が 1 つだけのときのみ）。処理意見には DI ファイルがなく、件名の行がない下書きからも作成できません。どちらも 400 を返します。レスポンスヘッダー X-Jtdt-Di-Valid は DTD 検査の合否（1 または 0）、X-Jtdt-Di-Notes は注意事項の件数です。

バッチ内容の counts：files、pages、cards（名刺）、cards_done、cards_failed、cards_pending、contacts（除外を除く）、confirmed、check。status：frames（複数枚モードで範囲の確認待ち）、recognizing、review。ポーリングして cards_pending が 0 になれば認識完了です。各名刺（pages[].cards[]）には認識後に engine（実際に使った OCR エンジン）、secs（その名刺の補正から抽出までの秒数）、ocr_secs（そのうち文字認識の秒数）が付きます。

範囲の調整（JSON）：{"cards": [{"id"?, "quad": [[x,y]×4], "rotate": 0|90|180|270, "memo"?}], "recognize": true?}。座標はページ画像のピクセルです。id のない範囲は新規、一覧にない範囲は削除されます。範囲と角度が変わっていない名刺は認識結果を残し、変えたものだけ再認識します。NaN、無限大、小さすぎる範囲は受け付けず、1 ページ最大 60 枚です。

取り込みモードの切り替え（JSON）：{"mode": "multi" | "single", "pages": [ページ番号…]?}。アップロード時にモードを間違えたとき、再アップロードせずに使います。指定したページだけ（省略時はバッチ全体）名刺を見つけ直し、そのページの認識結果と変更は消え、他のページはそのままです。multi は範囲確認（status=frames）で止まり、single はすぐバックグラウンドで認識します。認識中のときは処理中の 1 枚が終わるのを待ちます（最大 60 秒、超えると 409）。1 枚モードで pages[].multi_hint=true は、その画像に名刺が複数写っていそうなことを示します。

連絡先：fields は {"id", "key", "value", "status", "reason", "source", "ext"?, "label"?, "zip"?, "norm"?} の一覧です。key は name、name_en、title、department、company、company_en、vat、mobile、phone、fax、email、url、address、im で、電話、メール、住所などは複数持てます。status：auto（認識値）、check（要確認、reason に理由）、confirmed（人が確定）、deleted。source.method は ocr / qr / manual、source.box はその行の名刺画像上の位置（[left, top, width, height]）です。保存：PUT …/contacts/{id} に fields（全体）、notes（event / source / tags / memo）、status（check / confirmed / excluded）を付けます。status=confirmed のときはその連絡先の全項目を確定にします。再認識（retry）は手で直した・確定した項目を残します。すべて保存：POST …/contacts/save-all に {"items": [{"id", "fields"?, "notes"?}], "confirm_all"?: true} を付けると複数人をまとめて保存します。先に全体を検査し（1 件でも不正なら何も保存しない）、confirm_all=true のときは除外も確定もされていない連絡先をすべて確定にします（項目も人が確認したものとして扱います）。saved、confirmed とバッチ内容を返します。

出力（JSON）：format＝csv / xlsx / ods / vcf / json、scope＝confirmed（既定）/ all（未確認を含む）/ selected（ids を付ける）。表計算ファイルは table=true で開くとすぐ絞り込み・検索でき（XLSX は Excel テーブル、ODS はオートフィルター）、false はデータのみ。lang＝zh（中国語の列名）/ en（英語のコード）、columns で列と順序を選べます。CSV は encoding（既定 utf-8 / big5。Big5 にない文字は疑問符に化かさず 422）、bom（既定 true）と safe（既定 true：=、+、-、@、タブ、改行、先頭の空白で始まる値にアポストロフィを付ける）、JSON は include_source も指定できます。1 人 1 行で、2 つ目以降の電話やメールなどはそれぞれ別の列になり、列数は今回の出力で最も多い人に合わせます。電話、内線、郵便番号、統一番号は XLSX と ODS では文字列です。出力できる人がいないときは 409。export/preview は count、headers、先頭 5 行、skipped_check、excluded、および big5_missing（Big5 にない文字、最大 10 個）と big5_missing_count を返します。

個人用の名刺帳は本人（owner）だけが見られます。共有の名刺帳はメンバーの役割に従い、view は検索・閲覧・エクスポート、edit はさらに保存・編集・統合・削除・やり取りの記録ができます。見られない名刺帳は常に 404、閲覧だけなのに変更しようとすると 403 です。q は空白区切りのキーワード（それぞれがいずれかの項目かメモに含まれる必要があります）、tag はタグ全体です。やり取りの kind＝meeting / call / email / visit / other、at はタイムスタンプ（省略＝現在）。名刺帳に保存するとき、preview はメール → 携帯 → 氏名＋会社の順に同一人物かもしれない人を探します（matches[].reason）。merge はその人に名刺の記録（名刺画像を含む）を 1 件追加し、現在のデータを新しいものに置き換え、古いものは名刺の履歴に残ります。保存期間は名刺帳ごとに設定し（最終更新から数え、0＝無期限）、個人用の名刺帳は管理者の上限に従います。監査：business_card_book_query（キーワードは記録しない）、business_card_book_view、business_card_book_save、business_card_book_edit、business_card_book_merge、business_card_book_delete、business_card_book_export、business_card_interaction。共有の名刺帳とメンバーは管理者が「設定 → 名刺帳」で管理します（/admin/business-cards/api/…）。

名刺帳へのファイルのインポート（編集権限が必要）：形式は「以前の出力ファイルとの統合」と同じ（XLSX / ODS / CSV / VCF / JSON、上限も同じ）。アップロードは token、kind、headers、先頭 5 行、mapping、targets と自動の重複チェックの結果 items を返します。各行は {"row", "kind", "default", "who", "match", "dup_of"}、kind＝new（名刺帳にない、既定 add）/ match（メール → 携帯 → 氏名＋会社 で名刺帳の人が見つかった、既定 merge：その人に出所 import の記録が 1 件増え、現在のデータにファイルの値を補う）/ dup（同じファイルの dup_of 行目と同じ人、既定 skip。merge にするとその行がインポートされた人に統合）/ empty（空白行、スキップ）。照合の時点では書き込まず、apply で書き込んで一時ファイルを削除し、added / merged / skipped を返します。一時ファイルは約 2 時間で、期限切れは 410、他人や別の名刺帳の token は常に 404 です。重複のチェック：duplicates は groups（各グループの people と reasons：メール / 携帯 / 氏名と会社が同じ。A と B の携帯が同じで B と C のメールが同じなら 1 組）と can_edit を返し、統合は people/merge を使います。監査：business_card_book_import_upload、business_card_book_import（件数のみ）、business_card_book_duplicates。

9b. 複合機スキャン・取り込み API

FUJIFILM のボックス取得と RICOH のドキュメントサーバー取得（IM C2000、IM C2010、IM C2510、IM C3500、IM C3510）は実機で検証済みで、その他のメーカーと機種の取得は試験機能です。現在できるのは、複合機の追加、接続テストと機種識別、eSCL（AirPrint / Mopria スキャン）に対応した複合機からスキャンしてワークスペースへ直接保存すること、管理者が設定した共有複合機、FUJIFILM 複合機のボックスからの取得、Canon / Konica Minolta / SHARP の共有フォルダーからの取得、KYOCERA / RICOH からの直接取得（いずれも試験機能）です。Web のツールページと管理ページもこのエンドポイントを使っています。ツールは旧名「複合機から取り込み」で、v1.16.89 から「複合機スキャン・取り込み」に改名しました。URL とツール ID は変わりません。

各複合機は呼び出した本人のものです（API トークンで呼び出した場合はトークンの所有者）。他人の複合機は常に 404 を返し、存在するかどうかも明かしません。共有複合機は管理者が作成してメンバー（ユーザー、またはサブグループを含むグループ）を指定します。メンバーは表示、再テスト、スキャンができますが、名前の変更や除去はできません。ログインが無効な場合は、サーバー本体のブラウザーか有効な API トークン付きの呼び出しだけを受け付けます。

監査：すべての操作を監査ログに記録します（接続テスト、複合機の追加 / 名前変更 / 削除、文書の一覧表示、共有複合機とメンバーの設定）。スキャンと取り込みは 2 件記録します：送信時（mfp_scan_start、mfp_box_fetch、mfp_share_fetch。選んだ文書と原本を削除するかどうか）と完了時（mfp_job_done。実際の結果、ワークスペースに保存したファイル数、複合機から削除した原本）。パスワードと文書の内容は記録しません。

接続テストの安全範囲：接続先は社内ネットワークのアドレスだけ（プライベート IP。ループバック、リンクローカル、グローバルアドレス、このサーバー自身のアドレスは常に拒否）、Web ポート 80、443、8080、8443 だけです。送るのは GET（トップページと eSCL の機能一覧 /eSCL/ScannerCapabilities）だけで、認証情報や Cookie は送りません。リダイレクトは同じ機器内だけたどります。1 人あたり 5 分間に 10 回まで、同時に 1 つだけです。

ユーザーが自分で複合機を追加できるかは管理者が決めます（既定は許可。下の「利用設定」を参照）。オフのとき、一般ユーザーが接続テストや保存を呼び出すと 403（USER_DEVICES_DISABLED）になり、以前に自分で追加した複合機は一覧で paused: true となって、テスト・スキャン・取得はできませんが、名前の変更と除去はできます。共有複合機は通常どおり使え、管理者は制限されません。

順番待ち：同じ実際の機器（解決後のアドレスで判断）は一度に 1 つの処理だけを行います。接続テストは最大 30 秒待ち、それでも空かなければ 429（DEVICE_BUSY、waiting 付き）を返します。スキャンはバックグラウンドで順番を待ちます。1 台あたり最大 10 件（DEVICE_QUEUE_FULL）、同じ機器で 1 人あたり最大 2 件（OWNER_QUEUE_FULL）で、それを超えると 429 を返し、機器には何も送りません。

ジョブ記録の status：queued（順番待ち。ahead は前にある件数）、running（phase は checking / scanning / merging / downloading / saving）、done（pages、bytes、workspace_file_id）、error（error_code、error_message）、cancelled。kind は scan（スキャン）または box（ボックスからの取得）で、files は保存したファイルの一覧（name、pages、workspace_file_id、has_file）です。呼び出した本人のワークスペースだけに保存し、ほかの人は id を使っても参照もダウンロードもできません。settings.via は今回使ったプロトコル（例：{"protocol": "eSCL", "scheme": "https", "port": 443}）、tls_verified は証明書を検証できたかどうかです。

機器の機能範囲外の設定は 400（SCAN_OPTION_INVALID）、eSCL のない機器は 400（SCAN_NOT_SUPPORTED）、順番待ちが満杯なら 429 を返します。スキャン中のエラーは記録の error_code に入ります：SCAN_DEVICE_BUSY（誰かが機器を操作中）、SCAN_ADF_EMPTY、SCAN_AUTH_REQUIRED（スキャンにログインが必要な機器。まだ対応していません）、SCAN_NO_DOCUMENT、SCAN_BAD_DOCUMENT、SCAN_TOO_LARGE、SCAN_TIMEOUT など。認証情報は送りません。

一時保存して最後に 1 つの PDF に結合

原稿台ガラスは 1 回に 1 ページしかスキャンできません。毎回 "hold": true を付けてスキャンすると一時保存され（ワークスペースには保存されません）、プレビューを確認して次の原稿をスキャンし、最後に好きな順番で 1 つの複数ページ PDF に結合してワークスペースに保存できます。一時保存は 24 時間、1 人あたり最大 40 回（超えると 400 HOLD_TOO_MANY）、1 回の結合は最大 300 ページです。

GET  /tools/mfp-fetch/api/scans/held?conn_id={id}            # 還沒合併的暫存掃描（conn_id 選填）
GET  /tools/mfp-fetch/api/scans/{scan_id}/preview/{page}?w=240  # 第 page 頁（從 0 起算）的預覽 PNG；w 是 240 或 1200
POST /tools/mfp-fetch/api/scans/merge                        # 合併成一份 PDF 存進工作區（回新的掃描紀錄）
POST /tools/mfp-fetch/api/scans/discard                      # 清除暫存的掃描

結合の body：pages は [["スキャン id", ページ番号], …] で、その順番が結合後のページ順になります。不要なページは省けます。file_name は任意、release も任意で、あわせて消去する一時保存スキャン（全ページを削除したものなど）を指定します。結合に使った一時保存スキャンは消去されます（記録の workspace_note は MERGED_SOURCE になります）。呼び出し元のものでない、期限切れ、消去済みのソースは 404（MERGE_SOURCE_GONE）を返します。ワークスペースが無効の場合、結合結果は通常のスキャンと同じく一時領域に 24 時間保存され、本人がダウンロードできます。

curl -X POST http://localhost:8765/tools/mfp-fetch/api/scans/merge \
  -H "Authorization: Bearer YOUR_TOKEN" -H "Content-Type: application/json" \
  -d '{"pages": [["9f2c…", 0], ["a71b…", 0], ["9f2c…", 1]], "file_name": "合約"}' | jq

消去の body：{"scans": ["スキャン id", …]}。{"discarded": 消去した回数} を返します（呼び出し元のものでないスキャンは数えません）。

認証情報はこの要求でのみ使います（box/fetch ではそのジョブのメモリ内のみ）。データベース、ログ、通信記録には書きません。複合機が認証を求めたときは 1 回だけ送り、失敗したらそこで止めます（アカウントのロックを避けるため、別の組み合わせは試しません）。trace は通信記録（メソッド、パス、ステータスコード、認証方式と realm。認証情報は含みません）で、実機での検証時に照合に使います。

複合機側のエラーはすべて 422 を返します（401 は本サイト自体のログイン用）。code は次のとおりです：

  • 証明書を検証できない：TLS_UNTRUSTED。detail.certificate にフィンガープリントと内容があります。照合後に trust_sha256 を付けて再度呼び出します
  • 証明書が信頼したフィンガープリントと異なる：TLS_IDENTITY_FAILED。ボックスにはアクセスせず中止しました
  • 複合機が HTTP のみ：PLAIN_HTTP_NEEDS_CONSENT。allow_http: true を付けます
  • ボックスのパスワード、または複合機のアカウントが必要：AUTH_REQUIRED_BOX、AUTH_REQUIRED_USER
  • 認証失敗、または複合機が未対応の認証方式を求めた：AUTH_FAILED、AUTH_MODE_UNSUPPORTED
  • ボックスが見つからない、権限がない、WebDAV が無効、応答の形式が違う：BOX_NOT_FOUND、BOX_FORBIDDEN、WEBDAV_UNAVAILABLE、DAV_BAD_RESPONSE など
  • 複合機がこの要求を受け付けない（HTTP 406）：DAV_REQUEST_NOT_ACCEPTED。detail.stage は拒否された段階（probe の確認または list の一覧）、detail.profile はそのときの要求の形式（modern / legacy）

取得ジョブの記録はスキャンと同じものです（kind: "box"）。files は保存した各ファイル（name、pages、workspace_file_id）、items は文書ごとの結果（status、error_code、format_note、source：SOURCE_KEPT 元の文書が残っている / SOURCE_GONE 取得後に複合機からなくなった / SOURCE_UNKNOWN）です。一部の文書を取得できなかった場合も status は done で、error_code が BOX_PARTIAL になります。PDF への変換に失敗した場合（例：未対応の圧縮方式の TIFF）は元のファイルを保存し、format_note が PDF_FALLBACK_ORIGINAL になります。

9c. 押印申請 API

「承認済み案件のみ使用」の印章を使うときは、押印申請を出して段階ごとに審査を受け、すべて通過するとその印章の保管者が押印を確定します。管理者が機能を有効にし、アカウントログインも有効である必要があり、そうでない場合はすべて 404 を返します。すべてのエンドポイントにログインが必要で（ブラウザのログイン cookie、またはユーザーに紐づいた API トークン）、自分が関わる案件だけが見えます。関係のない案件・文書・添付はすべて 404 です。

10b. MCP（AI クライアント）

Claude Code、Codex CLI、OpenCode などの AI クライアントから、MCP（Model Context Protocol）経由でこのサイトのLLM を使わないツールを呼び出せます。既定ではオフで、管理者が「設定 → MCP（AI 連携）」でオンにします。

GET  /mcp/files/download    # 用一次性票證下載工作區的檔案

認証：Authorization: Bearer <API Token>。このトークンは設定ページで「MCP を許可」も有効にする必要があります。サインインが有効な場合はトークンをユーザーに割り当てる必要があり（API Token ページの「割り当てユーザー」列、または POST /admin/api/tokens/owner）、そのユーザーの権限で動作します（権限のないツールは表示も呼び出しもできません）。Origin ヘッダーを送る場合はサイト URL のオリジンでなければなりません。対応プロトコルバージョン：2025-11-25、2025-06-18、2025-03-26、2024-11-05。

AI 押印（v1.17.38）

AI が MCP 経由で、素材ライブラリのうち事前に AI 利用を許可した印鑑で押印します。既定ではオフで、次の条件が 1 つでも欠けると拒否します（AI のツール一覧にも表示されません）：

  1. サイトでアカウントのログインが有効
  2. 「設定 → MCP」で「AI 押印を許可」がオン
  3. API トークンがユーザーに紐付き、トークン一覧で「押印」がオン（別の人に紐付け直したり MCP をオフにしたりすると自動的に取り消し）
  4. ユーザーに「押印と署名」（割印は「割印」）のツール権限がある
  5. その印鑑が「設定 → 押印申請」で AI 利用を許可されており（使用モードは「直接使用」）、ユーザーが対象に含まれ、今日の上限に達していない

（1 日の上限は「箇所」単位：4 箇所押せば 4。確認と使用量の予約は同じトランザクションで行い、押印に失敗すると使用量を戻します）

アップロード画像や文字から生成した印鑑は受け付けず、印鑑の画像は AI に渡しません。「承認済み案件のみ使用」の印鑑は AI から一切使えません。

MCP ツール（条件がそろったときだけ表示され、上の公開ツールの一覧では個別に切り替えません）：stamp_list（使える印鑑）、pdf_stamp（押印と署名）、pdf_seam_stamp（割印）、stamp_request_status（確認待ちの件を確認）。

対応するエンドポイントは MCP の内部呼び出し用です：MCP 経由の呼び出しだけを受け付け（MCP を許可したトークンで直接呼び出すと上の規則で 403 になります）、Web のログインでもこれらで押印できません。AI は常に MCP の jtdt_run で上の 4 つの MCP ツールを呼び出します。ここではパラメータとレスポンスを説明するために挙げています：

GET  /api/ai-stamp/seals?tool=pdf-stamp        # 或 tool=pdf-seam-stamp
POST /tools/pdf-stamp/api/ai-stamp             # file + placements_json
POST /tools/pdf-seam-stamp/api/ai-seam-stamp   # file + asset_id + 騎縫章設定
GET  /api/ai-stamp/requests/{request_id}

placements_json は配列で、各箇所は {"asset_id", "page"（0 起）, "x_mm", "y_mm", "width_mm", "height_mm", "rotation_deg"}で、位置やサイズを省くと素材ライブラリでその印鑑に設定した値を使います。受け付けるのはこれらの項目だけです。1 件 50 箇所まで、数値は NaN と無限大を受け付けず、幅と高さは 0 より大きく 2000 mm 以下、角度は ±360 以内です。割印の設定項目は /api/pdf-seam-stamp（mode、group、edge、 size_mm、offset_mm、pos_mm、angle_deg、opacity、jitter_pos、jitter_angle、seed）と同じですが、受け付けるのは asset_id。受け付けないのは stamp、text、shape、color。

MCP の jtdt_run の例（files は先に /mcp/files/upload でアップロードしたワークスペースのファイル番号）：

{"tool": "pdf_stamp", "files": ["<file_id>"],
 "params": {"placements_json": "[{\"asset_id\": \"<seal id>\", \"page\": 0}]"}}

レスポンス：確認不要の印鑑は押印済みの PDF をそのまま返します（ヘッダー X-JTDT-AI-Stamp がこの件の番号）。確認が必要な印鑑は 202 {"status": "pending", "request_id", "expires_at"} を返し、トークンに紐付いた本人が Web の「AI 押印の確認」ページ（/ai-stamp）で承認すると、GET /api/ai-stamp/requests/{request_id} の status が approved になり file.file_id（本人のワークスペース）が付きます。承認と差し戻しは Web でログインしたときだけ（POST /ai-stamp/api/{request_id}/approve、POST /ai-stamp/api/{request_id}/reject）で、API トークン付きの要求は常に 403 です。24 時間処理されないと expired になりファイルは削除されます。承認時に条件を再確認し（印鑑の AI 許可と対象者、ツール権限、AI 押印と MCP のスイッチ、アカウントの有効）、いずれかが成り立たなくなっていれば 409 NO_LONGER_ALLOWED を返し、その件は void になりファイルは削除されます。1 人あたりの確認待ちは 20 件・500 MB まで（超えると 429 TOO_MANY_PENDING）。通知に書くのは印鑑名・トークン名・時刻だけで、AI が送ったファイル名は書きません。確認ページは GET /ai-stamp/api/pending、GET /ai-stamp/api/{request_id}/preview/{page} も使います。

エラー：条件を満たさないと 403（メッセージにコードが付きます。例：MCP_OFF、STAMP_OFF、TOKEN_NOT_MCP、TOKEN_NOT_ALLOWED、NOT_VIA_MCP、ASSET_NOT_ALLOWED）、1 日の上限を超えると 429。通常の /api/pdf-stamp、/api/pdf-seam-stamp は MCP 経由の呼び出しを拒否します（403）。

毎回監査イベント ai_stamp を記録します（承認 / 差し戻し / 期限切れは ai_stamp_decision）：ユーザー、トークン名、印鑑、ページ、入力と出力の SHA-256、確認の有無と確認者。印鑑の画像は含みません。出力 PDF の文書情報には表示されない JTDTAIStamp（番号と時刻）が入ります。管理者：GET /admin/mcp/ai-stamp（記録ページ）、GET /admin/mcp/ai-stamp.json、GET /admin/mcp/ai-stamp.csv（絞り込み asset_id、user_id、since、until、日付は YYYY-MM-DD）。印鑑ごとの AI 設定は PUT /admin/seal-request/api/assets/{asset_id} の ai（enabled、subjects、confirm、daily_limit）です。

12. 連携の例

Shell：job の完了を監視してダウンロード

#!/bin/bash
TOKEN="YOUR_TOKEN"
API="http://localhost:8765"

JOB=$(curl -fsSL -X POST "$API/api/llm-review" \
  -H "Authorization: Bearer $TOKEN" \
  -F "file=@filled.pdf" -F "template_id=vendor_form_v3" \
  | jq -r .job_id)

echo "Job: $JOB"

while :; do
  S=$(curl -fsSL "$API/api/jobs/$JOB" -H "Authorization: Bearer $TOKEN")
  STATE=$(echo "$S" | jq -r .status)
  PROG=$(echo "$S" | jq -r .progress)
  echo "  $STATE  $PROG"
  [ "$STATE" = "completed" ] && break
  [ "$STATE" = "failed" ] && { echo "Failed"; exit 1; }
  sleep 2
done

curl -fsSL "$API/api/jobs/$JOB/download" \
  -H "Authorization: Bearer $TOKEN" \
  --output reviewed.pdf
echo "Saved: reviewed.pdf"

14. レート制限 / 大きなファイルの上限

現時点で rate limit は内蔵していません。導入時にはリバースプロキシ（nginx / Caddy）で次を追加することをおすすめします：

  • client_max_body_size 100M（必須。設定しないと大きな PDF が拒否されます）
  • proxy_read_timeout 900s + proxy_send_timeout 900s（必須 —— LLM ツールの推論は 1 件あたり 5-15 分かかることがよくあり、既定の 60s では必ず 504 になります）
  • proxy_buffering off（LLM の streaming に適しています）
  • 多層の nginx 構成（自前の LLM proxy + jt-doc-tools で nginx が 2 台）ではどの層にも設定が必要です。1 層でも既定のままだと、その時点で切れます
  • 外部に公開する必要がある場合は、悪用を防ぐために limit_req_zone の追加をおすすめします

詳しくは OPS.md の「リバースプロキシ」の節と「504 Gateway Timeout のトラブルシューティング手順」をご覧ください。

14b. ユーザーのワークスペース（session 認証。Bearer API ではありません）

「マイワークスペース」はログイン session に紐づく web 機能で（cookie 認証）、外部向けの Bearer API ではありません。各ファイルがログインしたアカウント単位で分離されるためです。admin が「ワークスペース設定」で有効にする必要があり、無効のときは以下のエンドポイントはすべて 404 を返します。

エンドポイントメソッド説明
/workspaceGET「マイワークスペース」ページ
/workspace/api/listGET自分のファイルを一覧表示（?accept=pdf,png で絞り込み）+ 容量 + 保持時間。各ファイルには preview（サムネイルの有無）と kind（pdf / image / office / text / audio / video）が付きます
/workspace/api/countGETファイル数（サイドバーのバッジ用）
/workspace/savePOST保存：job_id（サーバー側で job の結果を複製）または file（bytes を直接アップロード）。形式は内容で判定します：PDF / PNG、Office 文書、プレーンテキスト、録音 / 録画ファイル（.m4a / .mp3 / .wav / .aac / .ogg / .opus / .flac / .mp4 / .mov / .mkv / .webm）。録音ファイルには別に 1 ファイルの上限（max_audio_mb）があり、超えると 413 を返します
/workspace/file/{file_id}GETファイルの取得（?dl=1 でダウンロード）
/workspace/thumb/{file_id}GETサムネイル（PDF は 1 ページ目をレンダリング / PNG は元画像）。プレーンテキストと録音ファイルには 1×1 の透明なプレースホルダー画像（Cache-Control: no-store）を返すので、preview で判断し、サムネイルとして使わないでください
/workspace/deletePOST削除（file_id）

/tools/meeting-transcribe/from-workspacePOST自分のワークスペースにある録音ファイルを文字起こしに渡します（JSON {"file_id": "…"}、再アップロードなし）。レスポンスは /tools/meeting-transcribe/upload と同じです。他人のファイル / 存在しない → 404、録音ではない → 400、音声サービスが未設定 → 503

14c. ユーザーの通知と受信トレイ（session 認証。Bearer API ではありません）

§14b のワークスペースと同じ性質で、ログイン session（cookie）に紐づくため、外部向けの Bearer API ではありません。 内容がログインしたアカウント単位で分離されるためです。未ログインの場合は常に 401 / 302 を返します。

エンドポイントメソッド説明
/api/my/notifyGET自分の通知設定を読み取ります（ジョブの完了時に通知するか、どのチャネルを使うか）
/api/my/notifyPOST自分の通知設定を保存します
/api/my/inboxGETサイト内通知の一覧（未読を優先）
/api/my/inbox/seenPOST既読にする（id または all=1）
/api/my/zulip-linkGETZulip 連携の状態：連携済みのアカウント（linked）と進行中の連携（pending：コード、有効期限、メッセージを送るボット、確認待ちの Zulip アカウント candidate）
/api/my/zulip-link/startPOST1 回限りの連携コードを発行（10 分間有効）。Zulip で通知ボットにダイレクトメッセージで送ります

15. 変更履歴

API のインターフェースは SemVer に従います：minor バージョン（1.4.x → 1.5.x など）は後方互換を保証し、major バージョン（1.x → 2.x）でのみ breaking な変更を行います。エンドポイントの追加は breaking には含みません。
