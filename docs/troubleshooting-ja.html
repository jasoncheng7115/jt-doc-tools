アップグレードが git fetch failed で止まる（would clobber existing tag）

症状　jtdt update が git fetch failed と表示して 中断し、サービスは元のバージョンに戻され、原因がわかりません。

原因　本プロジェクトは 2026-09-13 に git の履歴を書き換えており（誤って版管理に入ったデータを除去するため）、 すべてのタグが新しい commit を指しています。ローカルのタグが古いものを指したままだと、 git fetch --tags（--force なし）は 1 件ずつ would clobber existing tag を報告し、終了コード 1 で終わります。

対処　次の 1 行を実行すれば恒久的に解決します（.git の中の ref だけを操作し、 ユーザーデータには触れません）：

Linux / macOS
sudo git -C /opt/jt-doc-tools fetch --tags --force origin
Windows（管理者として PowerShell を実行）
git -C "C:\Program Files\jt-doc-tools" fetch --tags --force origin

影響を受けないもの：tarball でのインストール（.git がありません）、Windows インストーラー、 および 2026-09-13 より後にインストールしたもの。v1.15.41 以降は修正済みです。

Health check timed out / failed（でもサービス自体は正常）

症状　更新処理の最後でタイムアウトしますが、ブラウザーでは開けます。

原因　待ち受けアドレスやポートを変更したあと（jtdt bind）、 古いバージョンのヘルスチェックは、更新を実行したシェルの環境変数からアドレスを読んでいました —— そこには何も設定されていないため、 常に 127.0.0.1:8765 を調べにいきます。企業環境の http_proxy によって「自分への接続」がプロキシサーバーへ送られることもあります。

対処　v1.15.15 以降で修正済みです（サービスマネージャー自身の設定を読み、プロキシを経由せず直接接続し、 調べたアドレスとログの最後 20 行を表示します）。まずそのバージョン以上にアップグレードしてください。 それでもタイムアウトする場合は jtdt logs の最後の数行をご覧ください。

別のケース　v1.15.11 ～ v1.16.10 から更新すると、最後に Health check failed と表示され、Service state は RUNNING / active。Windows ではログが見つからないとも表示されます。

原因　これらのバージョンのヘルスチェック自体に不具合があり（import が 1 行抜けていた）、サービスの状態に関係なく失敗と判定していました。Windows と macOS はログの場所も間違えていました。

対処　ブラウザで開ければ更新は成功しています。対応は不要です。v1.16.11 で修正済みですが、v1.16.11 への更新そのものではまだ一度このメッセージが出ます（チェックを実行するのは更新前のバージョンのため）。次回の更新からは出ません。ログの実際の場所：Windows は C:\ProgramData\jt-doc-tools\Logs\（jtdt-svc.err.log と jtdt-svc.out.log）、macOS は ~/Library/Logs/（jt-doc-tools.err と jt-doc-tools.log）、Linux は journalctl -u jt-doc-tools。

CERTIFICATE_VERIFY_FAILED（企業の TLS 検査環境）

症状　更新、OCR 言語ファイルのダウンロード、LLM / SSO への接続で証明書の検証に失敗します。

原因　会社の TLS 検査プロキシが外部の証明書を自社の CA に差し替えており、Python / uv は既定でその CA を認識しません。

対処　プログラムは自動的に OS の信頼ストアを使います（truststore）ので、 ほとんどの環境では設定は不要です。それでも失敗する場合は、企業の CA を OS の信頼ストアに取り込んでください。 一時的に回避するには JTDT_TLS_INSECURE=1 を使います（確認済みの社内ネットワークでのみ）。

git のないインストールは更新できません

症状　jtdt update が git を見つけられない、またはここは git リポジトリではないと表示します。

原因　マシンに git がない場合、ワンライナーのインストールは圧縮ファイルをダウンロードする経路に切り替わり、 できあがったディレクトリには .git がありません。

対処　git をインストールしてから、ワンライナーのインストールをもう一度実行してください —— その場で git リポジトリに取り込みます（既存の .venv とデータは保持されます）。以降は通常どおり更新できます。

Windows で git が見つからない、または winget でのインストールを求められる

症状　git をインストールした直後なのに見つからない。または Windows Server に winget がない。

原因　インストールしたばかりのプログラムは登録情報の PATH しか更新しないため、すでに開いている端末（新しいタブを含む） が見ているのは古い PATH のままです。また Windows Server 2019 / 2022 には winget が同梱されていません。

対処　そのままもう一度実行するだけで済みます。再起動は不要です —— プログラムは 「PATH → 登録情報 → 標準のインストール場所」の 3 段階で探します。Server 版では git の公式サイトからインストーラーをダウンロードしてください。

[X] uv venv failed（Windows のアップグレード時）

症状　インストーラーで既存のインストールに上書きすると失敗します。無人インストールでは固まったように見えます。

原因　サービスがまだ動いていて、python.exe が仮想環境のファイルを掴んでいるため、 削除できません。古いバージョンの失敗ダイアログには無人時の既定値がないため、誰も押せないボタンを待ち続けます。

対処　v1.15.37 以降で修正済みです（インストール前にサービスを停止し、プロセスが本当にファイルを解放するまで待ち、 すべてのダイアログに無人時の既定値を設定しました）。固まったときは手動でサービスを停止してからインストールしてください。 インストーラー自身のログは C:\ProgramData\jt-doc-tools\Logs\installer.log にあります。

アップグレード時にディスク容量が足りない

症状　バックアップの段階で失敗し、しかもサービスはすでに停止しています。

原因　アップグレードの前にデータディレクトリを完全にバックアップし、3 世代を保持します。

対処　v1.15.17 以降はサービスを停止する前に容量を確認し、どれだけ足りないかを表示します。 バックアップでも、自分で再生成できるもの（統一番号データベース、一時ファイル、ジョブの結果）はスキップします。 実測で 1 世代あたり 1.93 → 0.56 GB になりました。空き容量を確保してから再実行してください。

attempt to write a readonly database

症状　sudo で CLI コマンドを実行したあと、サービスがデータベースに書き込めなくなります。

原因　root で実行すると新しく作られるファイルが root の所有になりますが、サービスは自分のアカウントで動いています。 最も起きやすいのは jtdt reset-password です —— 復旧作業をしたのにログインできなくなります。

対処　v1.15.16 以降、すべての CLI コマンドは終了時にデータディレクトリの所有者をサービスアカウントへ戻します。 古いバージョンでこの状態になった場合は、手動で所有者を修正してください（Linux： sudo chown -R jtdt:jtdt <データディレクトリ>）。

変換が 503 を返す、または出力した中国語が四角になる

症状　オフィス文書関連のツールが「サービスが一時的に利用できません」と返します。 または出力した PDF の中国語が白抜きの四角になります。

原因　このマシンに LibreOffice / OxOffice がないか、日中韓フォントがありません。

対処　エラーメッセージに何をインストールすべきかが表示されます。Linux では libreoffice（または OxOffice）と fonts-noto-cjk をインストールしてください。 管理エリアの「システム依存」ページに、不足しているものが 1 件ずつ表示されます。

リモートのユーザーがアップロードすると「CSRF token が見つからないか正しくありません」

症状　サーバーのローカルではどう試しても正常なのに、別のパソコンから接続したときだけ失敗します。 ログインも繰り返しログインページへ戻されることがあります。

原因　リバースプロキシが X-Forwarded-Proto を https に固定しているのに、サイトは実際には http です —— そのためバックエンドは cookie に Secure を付け、ブラウザーは平文の接続ではその cookie をそのまま破棄します。 http://localhost はブラウザーの安全なオリジンの例外なので、ローカルでは再現できません。

対処　リバースプロキシに実際のプロトコルをそのまま渡させてください（IIS では rewriteMap で {HTTPS} を https/http に変換します）。 あるいはサイト自体を HTTPS にしてください。例は次をご覧ください OPS.md。

「音声サービスに接続できません」またはタイムアウト

症状　音声サービス設定ページの「接続をテスト」が失敗する。認識モードのドロップダウンに「一覧を取得できませんでした：音声サービスに接続できません」と表示される。または録音の送信に失敗する。

原因　送信先の入力ミス（ホスト、ポート、http / https）、ファイアウォールによる遮断、相手側サービスの停止 —— 証明書の検証失敗の可能性もあります。相手が自己署名証明書を使っている場合、接続は TLS の段階で拒否されますが、画面には「接続できません」としか表示されません。

対処　送信先は相手から受け取った文字列をそのまま貼り付けます（例：https://ホスト:8790/api/v1）。本システムのマシンで curl https://ホスト:8790/api/v1/health を試してください。接続できなければネットワークかアドレスの問題、-k を付けたときだけ接続できるなら証明書の問題です。相手の証明書（PEM）を「相手の証明書」欄に貼り付け、相手が公開している SHA-256 フィンガープリントと照合してから保存してください。検証を無効にして回避しないでください。送信のたびに API キーを渡すため、検証を無効にすると誰でも相手になりすませます。

「音声サービスがこの API キーを受け付けません（401）」または「この操作の権限がありません（403）」

症状　「接続をテスト」または送信時に、どちらかのメッセージが表示される。

原因　この 2 つは別の状況です。401：キーの入力ミス、相手側での失効、またはヘッダー全体を貼り付けてしまった場合。403：キーは正しいが、この操作の権限がない場合です。入力ミスや失効を調べても原因は見つかりません。相手のヘルスチェックはキーを検証しないため、それだけでは分かりません。そのため「接続をテスト」ではキーを使った問い合わせも行います。

対処　401：「API キー」にはキーそのもの（相手から受け取った文字列）だけを貼り付けます。Authorization: Bearer ヘッダーは本システムが組み立てます（接頭辞を貼り付けても自動で取り除かれます）。確認しても拒否される場合は、そのキーがまだ有効か相手に確認してください。403：相手の管理者にキーへ権限を追加してもらってください。不足している権限は本システムのサービスログ（jtdt logs）に記録されています。

「音声サービスがこのマシンのアドレスを受け付けません。管理者に『録音ファイルの外部アドレス』を先方の許可リストへ追加してもらってください」

症状　録音の送信に失敗し、メッセージの末尾にホスト名が付いている。

原因　音声サービスは許可リストにあるアドレスからしか録音ファイルを取得せず、本システムの「音声ファイルの公開アドレス」がリストにありません。

対処　メッセージ末尾のホスト名を音声サービスの管理者に伝え、許可リストに追加してもらいます。「音声ファイルの公開アドレス」を変更したら、新しいアドレスも追加してもらってください —— 同じシステムに社内から直接つなぐ経路とリバースプロキシ経由の経路がある場合、入力した方が相手から見えるアドレスになります。

「録音ファイル URL に到達できませんでした」または「URL の有効期限が切れていました」

症状　録音の送信に失敗し、「音声サービスがこちらの録音ファイル URL に到達できませんでした」「音声サービスが録音ファイルを取りに来たとき、URL の有効期限が切れていました」「音声サービスが録音ファイルを取りに来たとき、こちら側で拒否しました（401 / 403）」のいずれかが表示される。

原因　録音ファイルは本システムから送るのではなく、相手が取りに来ます。本システムは短時間だけ有効な署名付き URL（/api/speech/audio/…?exp=…&sig=…、ログイン不要、期限が来ると自動で無効）を渡します。「音声ファイルの公開アドレス」がブラウザのマシンからしか届かない名前（localhost など）になっている、途中のファイアウォールやリバースプロキシで遮断されている、またはリバースプロキシの前段にログイン認証がある場合、相手は取得できません。

対処　「音声ファイルの公開アドレス」には音声サービスのマシンから到達できるアドレスを入力します（設定ページはブラウザのアドレスから推定しません。推定を誤ると「使える人と使えない人がいる」状態になります）。リバースプロキシの前段に SSO や Kerberos などのログイン認証がある場合は、/api/speech/audio/ を通してください。この部分は署名で保護されています。URL の期限切れは順番待ちが原因ではありません。相手は送信を受け取るとすぐに取得し、その後どれだけ待ってもこの URL を再び取りに来ることはありません。ほとんどは送信前の再試行や待ち時間が長すぎた場合です。もう一度送信してください。

「順番待ち（前に N 件）」のまま進まない、または「N 分待ちましたが音声サービスから結果が報告されないため、先方に取り消しを依頼しました」

症状　文字起こしを送信した後、ずっと順番待ちと表示される。または順番が来た後に長く処理が続き、最後に上のメッセージで失敗する。「音声サービスのキューが満杯です。しばらくしてから送信してください」と表示されることもあります。

原因　音声サービスの GPU は一度に 1 件だけ処理し、残りは順番待ちになります。前の件数には他の人の処理も含まれます。順番待ちの間は前に何件あるかが画面に表示され、その時間は待機の上限に含めません。順番が来ると、認識と補正の進捗が進みます。本システムは順番が来てから計時し（15 分と録音の長さの半分のうち大きい方）、超えると先方にこの処理の取り消しを依頼します。順番待ちそのものは最長 4 時間まで待ちます。

対処　順番待ちの間は順番が来るまでお待ちください。長い録音は、他の人が長い会議を送っている時間帯を避けてください。順番が来た後にタイムアウトする場合や、4 時間を超えて順番待ちになる場合は、音声サービス側に GPU サーバーの状態を確認してもらってください。

「音声サービスは成功を報告しましたが、文字起こしが 1 区間もありませんでした」

症状　このメッセージで文字起こしが失敗する。録音には明らかに発言がある。

原因　認識結果を返している途中で音声サービスが再起動し（更新またはクラッシュ）、途中までの結果が完全なものとして扱われました。最も多いのは 1 区間もない場合です。本システムは 0 区間を必ず失敗として扱い、空の文字起こしを成功として渡すことはありません。

対処　もう一度送信すれば、たいていは解決します。何度も起きる場合は、サーバーが更新中または再起動中でないか音声サービス側に確認してもらってください。

録音の最後に長く文字がない　録音の最後に 1 分を超えて文字がまったくない場合、結果画面にその空白の長さが表示されます。音声サービスは 2026-09-23 から「前半だけが返る」問題を修正済みのため、このお知らせは多くの場合、録音の止め忘れや、拍手・音楽で終わっていることを示します。その時間に実際に発言があった場合は、もう一度送信してください。

「音声サービスがこの言語設定を受け付けない」

症状　言語を選ぶと、送信した直後に失敗する。

原因　音声サービスは、現在の認識モードが対応している言語しか受け付けません。v1.16.8 以前は画面が「中国語」を zh として送っていましたが、音声サービスが求めるのは zh-Hant のため、中国語を選んだ処理はすべて拒否されていました（v1.16.9 で修正）。その後も発生する場合は、管理者が選んだ認識モードがその言語に対応していない可能性が高いです（例：台湾語のモードは台湾語と中国語のみ対応）。

対処　「自動判定」を選んで再送信してください。繰り返し発生する場合は、管理者に「音声サービス（JTLW）」で現在の認識モードが対応している言語を確認してもらってください（認識モードを選ぶと下に表示されます）。

中国語の会議が全体を通して英語として認識される（またはその逆）

症状　文字起こしのほとんどが誤字になる、または会議全体が別の言語になる。言語は「自動判定」を選んでいた。

原因　「自動判定」は録音の冒頭約 30 秒の発話だけで会議全体の言語を決めます。冒頭で誰かが別の言語を話すと（英語で始めた場合など。20 秒で十分です）、全体が誤った言語で認識されます。音声サービスの実測では、中国語が中心で冒頭が英語の会議の場合、中国語の文の誤り率が 15% から 88% に上がりました。冒頭の無音や雑音は影響しないので、削る必要はありません。

対処　「言語」で会議全体の言語を選び、もう一度送信してください。中国語と英語の文が入れ替わる会議では、多く使われている方の言語を選んでください。もう一方の言語の文はほとんど正しく認識されません（中国語の文の中に英語の用語が混ざる程度なら問題ありません）。

「会議録音の文字起こし」がグレー表示になる、または「音声サービスがまだ設定されていません」と表示される

症状　サイドバーやホーム画面からそのツールを開けない。ツールのページを開いても設定の案内しか表示されない。

原因　このツールは外部の音声サービスに依存しており、管理画面で有効になっていない、または送信先と API キーが揃っていないあいだは、意図的にグレー表示になります。見た目は普通なのに押すと失敗するアップロード欄を出さないためです。

対処　管理画面の「音声サービス（JTLW）」で有効にし、送信先・API キー・音声ファイルの公開アドレスを入力して「接続をテスト」で確認してから保存してください。ほかの 49 個のツールには影響しません。

それでも解決しませんか？

次のものをあわせて添えていただけると、解決がずっと早くなります：

  • OS とバージョン、jtdt status の出力
  • jtdt logs の最後の 20 行
